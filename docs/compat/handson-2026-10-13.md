# Hands-on compatibility run — 2026-10-13 (credential-free)

- **Task:** `p0-compat-handson`, owner-reduced scope (decision 2026-10-13): **this Mac** plus **one Linux worker in a Docker container** instead of the seven physical nodes.
- **Rule:** no model credentials, no prompt ever sent to a model, no provider endpoint contacted. Every server bound `127.0.0.1` with a random per-run secret; every runtime ran with a throw-away `HOME`/`XDG_*` (and `CODEX_HOME`), so no real login or config was read or changed.

## Findings

1. **Codex sandbox inside Docker fails closed.** With Docker's default seccomp profile, bwrap cannot create a user namespace; Codex exits 1 and runs nothing (good: no silent unsandboxed run). It works with `seccomp=unconfined` + `apparmor=unconfined`. Consequence for ADR-0007: a Linux worker that itself runs in a container cannot offer the Codex `runtime-sandbox` without loosening the container's seccomp profile (or a custom profile that allows `unshare(CLONE_NEWUSER)`) — prefer workers on the host OS, or treat the container as the sandbox (`externalSandbox`).
2. **Probe gap:** `remyral-worker probe` reports `runtime-sandbox` *available* (Codex: bubblewrap) in that container although bwrap cannot create a namespace there. The probe should run a real namespace check (e.g. `bwrap --unshare-user --ro-bind / / true`) before claiming it — follow-up for `p3-sandbox` / the probe owner.
3. **`CODEX_HOME` must not be under `/tmp` on Linux.** Codex then refuses to create its helper aliases ("Refusing to create helper binaries under temporary dir") and bwrap fails with `execvp codex-linux-sandbox: No such file or directory` (fails closed). The adapter's per-job `CODEX_HOME` (T7) must live outside `/tmp`, e.g. under the worker's data dir.
4. **Fail-open servers confirmed on both platforms** (OpenCode without password, OpenHands without key; OpenHands also binds all interfaces when a key is set and `--host` is omitted). The worker self-test and adapter rules (ADR-0012 rule 2: random secret, explicit `127.0.0.1`, verify 401 first) stay mandatory.
5. **Start-up times:** the first OpenHands start after a fresh install on the Mac took longer than 120 s (bytecode compilation); later starts were seconds. OpenCode's first `GET /doc` took more than 5 s. Adapter start timeouts must allow for a cold first start.
6. **Linux arm64 binaries:** every pinned runtime has a working glibc arm64 build (Claude `linux-arm64`, Codex `linux-arm64`, OpenCode `linux-arm64`, Pi pure JS, OpenHands pure Python on CPython 3.12 arm64). This was a Docker Desktop VM, **not Raspberry Pi hardware**: page size, memory fit and performance on the Pi stay U.
