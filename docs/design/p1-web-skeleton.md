# Design note: web console skeleton and sign-in flow (P1)

- **Status:** Implemented
- **Date:** 2026-10-13
- **Backlog:** p1-web-skeleton
- **Decisions applied:** ADR-0002 (monorepo/toolchain), ADR-0009 (human authentication, Accepted),
  docs/design/p1-master-auth.md (auth API, cookies, CSRF, CSP)
- **Threat model:** T-CP-1, T-CP-2, T-SEC-1

## 1. Scope

`apps/web` (`@remyral/web`) is the operator console. This task delivers the frame and the complete
sign-in flow against the master's existing auth API; every functional section is an empty state that
names the backlog task that fills it.

| Screen                  | Reached when                                                          | Master call(s)                                               |
| ----------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------ |
| Sign in                 | no full session                                                       | `POST /auth/login`                                           |
| Authenticator code      | login answered `mfa_required`                                         | `POST /auth/totp/verify`                                     |
| Recovery code           | "Use a recovery code instead" on the code step                        | `POST /auth/recovery`                                        |
| Add authenticator       | login answered `enrollment_required`                                  | `POST /auth/totp/enroll/start`, `POST /auth/totp/enroll/confirm` |
| Recovery codes          | enrollment confirmed (codes returned once)                            | —                                                            |
| Shell                   | full session                                                          | `GET /auth/session`, `POST /auth/logout`, `POST /auth/logout-all` |
| Step-up dialog          | a privileged call returns `403 step_up_required`, or "Confirm now"    | `POST /auth/step-up`                                         |

Shell sections and the tasks that fill them: Fleet (`p5-fleet-ui`, `p2-pairing`, `p2-heartbeat-caps`),
Jobs (`p5-composer`, `p5-live`, `p4-job-store`), Approvals (`p5-live`, `p4-approvals`), Audit
(`p5-search-audit`), Settings (`p5-rbac-api`, `p5-notifications`). Settings already shows the session
timing, logout / logout everywhere and the step-up control.

Screenshots (mobile 390×844 @2x and desktop 1280×800, light; two dark): `docs/design/screens/p1-web/`.
They are regenerated by the e2e suite and show throw-away users from the e2e database.

## 2. Stack and choices

| Concern      | Choice                                                                                                                                                                                                                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| UI           | React 19.3.0, `react-dom` 19.3.0, StrictMode.                                                                                                                                                                                                                                                          |
| Build        | Vite 8.3.4 + `@vitejs/plugin-react` 6.1.2; output is static files (`index.html` + hashed `assets/`), no inline script or style (checked by the CSP e2e test).                                                                                                                                          |
| Styling      | Tailwind CSS 4.3.3 via `@tailwindcss/vite`. Semantic colour tokens (`--c-*` → `bg-surface`, `text-muted`, …) switch on `prefers-color-scheme`; system font stacks, no web fonts, no CDN, no icon font (inline SVG).                                                                                     |
| Routing      | **React Router 8.4.0, declarative mode** (`BrowserRouter`/`Routes`). Chosen over TanStack Router: the console needs a handful of flat routes plus guards, which declarative mode covers without a code generator, Vite plugin or loader/data layer. Data loading stays in explicit hooks; if later sections need loaders, React Router's data mode is an in-place upgrade. |
| State        | One `AuthProvider` (React state, no library). Server stages map to client states `checking → signedOut → secondFactor(totp \| recovery) \| enrollment → recoveryCodes → signedIn`. The server is authoritative; the client state only selects a screen.                                                   |
| API client   | `fetch` wrapper (`src/api/client.ts`): `/api` prefix, `credentials: 'same-origin'`, `cache: 'no-store'`, `redirect: 'error'`, structural validation of every response, errors keep the master's `error` code and `message`.                                                                              |
| Tests        | Vitest 5 + Testing Library (jsdom 30.1.2) for components/state; Playwright 1.64.0 (Chromium only) end to end.                                                                                                                                                                                          |

### Behaviour details

- **Generic errors.** The UI prints `message` exactly as the master sends it (`Invalid credentials.` for
  every factor failure, unknown user and locked account). It adds no hint of its own about which factor
  failed. Client-side validation (empty fields, not 6 digits) never reaches the API.
- **Rate limit / lockout.** A `429` shows the master's message plus "You can try again in …" from
  `Retry-After`, and the submit button stays disabled until it elapses. Lockout is deliberately
  indistinguishable from a wrong password (ADR-0009 §6), so nothing more can be shown.
- **Pending session ended** (expired after 5 minutes, or destroyed after 5 wrong codes): the master
  answers `401 unauthorized` instead of `invalid_credentials`; the UI returns to the sign-in form with
  "Your sign-in attempt has ended. Sign in again." A `401` on a full session does the same with "Your
  session has ended."
- **Enrollment start runs once** per attempt (in-flight guard): every call creates a new server-side
  secret, so a double click or StrictMode re-render must not replace the QR code the user is scanning.
- **Recovery codes** are rendered once from the confirm response, held only in React state, offered as
  "Copy all" (Clipboard API) and "Download .txt" (a `blob:` URL revoked on unmount), and the user must tick
  "I have stored these recovery codes in a safe place." before continuing.
- **Step-up.** `StepUpProvider.run(action)` runs a privileged call; on `403 step_up_required` it opens the
  modal (`<dialog>`: focus trap, Escape cancels, inert background), verifies a fresh code via
  `POST /auth/step-up` and retries the call once; cancel rejects with `StepUpCancelledError`. Later tasks
  (p2-pairing approvals, p4-approvals, p5-rbac-api) wrap their privileged calls in it.
- **Reload behaviour.** A full session survives reloads (`GET /auth/session` on start). A reload during
  the second factor or enrollment returns to the sign-in form, because the master has no endpoint that
  reports a pending stage (see §6, proposal 2); the abandoned pending session expires after 5 minutes.

### Accessibility and layout

Every input has a visible `<label>`; errors are linked with `aria-describedby` and `aria-invalid`; API
errors sit in an `aria-live` region below the submit button (so nothing above the user's focus moves);
the first field of each step is autofocused; skip link to the main content; the account menu closes on
Escape and returns focus; nav is a left sidebar on ≥ 768 px and a bottom tab bar on phones (thumb reach,
safe-area aware); 44 px tall touch targets on mobile; the QR image has fixed dimensions and a reserved box
(no layout shift while it decodes); `scrollbar-gutter: stable`; `prefers-reduced-motion` honoured. Code
inputs use `inputmode="numeric"`, `autocomplete="one-time-code"` and accept pasted "123 456".

## 3. Serving: same origin for UI and API

The console and the API **must share one origin**: the session cookie is `__Host-ras` (HttpOnly,
SameSite=Strict) and the CSRF double-submit cookie `__Host-ras-csrf` must be readable by the page.

- **Development.** `pnpm --filter @remyral/web dev` serves on `http://127.0.0.1:5173` and proxies `/api/*`
  to the master (`REMYRAL_MASTER_ORIGIN`, default `http://127.0.0.1:8080`), stripping the `/api` prefix.
  Chromium and Firefox keep `Secure` cookies on `127.0.0.1`/`localhost` (see admin-bootstrap §6).
- **Production.** `pnpm --filter @remyral/web build` writes static files to `apps/web/dist/`. The ingress
  (Coolify/Traefik, p1-coolify) serves them on the same host as the API:
  - `/api/*` → master, **strip the `/api` prefix** (the master's routes are `/auth/*`, `/healthz`, …).
  - everything else → static files; unknown paths fall back to `index.html` (client routing).
  - `assets/*` are content-hashed: `Cache-Control: public, max-age=31536000, immutable`; `index.html`:
    `no-cache`.
  - static responses carry the **same security headers as the master**: the CSP from
    `apps/master/src/app.ts` (`default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'
    data:; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors
    'none'`), HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.
  - `/api` was chosen so UI routes (`/jobs`, `/fleet`, …) can never collide with present or future API
    routes and the ingress needs one rule instead of a list of API paths.

## 4. Security review

| Threat / requirement                    | Mitigation                                                                                                                                                                                                                                                                                       | Residual / follow-up                                                                                                         |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Session theft via script (XSS → token)  | The session id exists only in the HttpOnly cookie; the bundle never reads, stores or logs it. No `localStorage`/`sessionStorage` use at all (asserted in e2e). No `dangerouslySetInnerHTML` anywhere.                                                                                               | A successful XSS could still act within the session (CSP below is the main defence).                                          |
| XSS / injected markup                   | React escaping only; strict CSP without `unsafe-inline` works for the production build (e2e `csp.spec.ts` serves `vite preview` with the master's live CSP header and fails on any `securitypolicyviolation`).                                                                                      | The dev server needs inline styles (Vite HMR) and is never exposed.                                                           |
| Untrusted SVG (QR code)                 | The master's `qrSvg` is turned into `data:image/svg+xml;base64,…` and shown in `<img>`; SVG as an image cannot run script, load resources or touch the DOM, so even a malicious string is inert. Non-SVG input is rejected. `img-src data:` is already in the master CSP.                            | —                                                                                                                            |
| `otpauth://` link                       | Rendered as a link only if it matches `^otpauth://totp/[^\s"'<>]+$`.                                                                                                                                                                                                                              | —                                                                                                                            |
| CSRF                                    | Every non-GET request echoes `__Host-ras-csrf` in `X-CSRF-Token` (read fresh each request because the master rotates it); SameSite=Strict; same-origin `fetch` with `redirect: 'error'`.                                                                                                          | —                                                                                                                            |
| Factor/account enumeration              | Master messages shown verbatim; the client adds none; unknown user and wrong password look identical (e2e).                                                                                                                                                                                        | —                                                                                                                            |
| Secrets in the bundle                   | No configuration is compiled in (no `import.meta.env` secrets, no API keys); the only build-time variable is the dev proxy target, which lives in `vite.config.ts` and never reaches the bundle.                                                                                                    | —                                                                                                                            |
| Secret shown on screen (TOTP seed, recovery codes) | Displayed only during enrollment, kept in component state, never persisted; downloads use a revocable `blob:` URL.                                                                                                                                                                      | Shoulder surfing/screen recording are out of scope.                                                                           |
| Third-party code at runtime             | No fonts, CDNs, analytics or icon services; all dependencies are pinned exactly and bundled.                                                                                                                                                                                                      | Supply-chain controls (SBOM, scanning) in p7-supply-chain.                                                                    |
| Open redirect after login               | The post-login return path is used only if it is an app-relative path (`/…`, not `//…`).                                                                                                                                                                                                         | —                                                                                                                            |
| Clickjacking                            | `frame-ancestors 'none'` on API responses; the ingress must send it for static files too (§3).                                                                                                                                                                                                    | Ingress configuration is p1-coolify.                                                                                          |

## 5. Tests

- `pnpm test` (part of `pnpm verify`): 29 web tests — API client (CSRF header on POST only, no
  Content-Type on body-less POSTs, same-origin/no-store/no-redirect, verbatim error code + message,
  `Retry-After`, network/malformed responses), QR/otpauth sanitising, login validation and focus,
  verbatim errors, 429 countdown + disabled submit, TOTP field attributes and paste normalisation,
  pending-session expiry, recovery-code path, one-shot enrollment start, QR as `<img>` (no inline SVG),
  recovery-code confirmation gate and download name, nav placeholders, logout/logout-all, 401 → signed
  out, step-up retry/cancel/pass-through.
- `pnpm --filter @remyral/web e2e` (separate; first run `pnpm --filter @remyral/web e2e:install` to fetch
  Chromium): 11 tests against the **real master** (`apps/master/dist`, unmodified) and the Vite dev
  server, plus the production build under CSP. Setup recreates the database `remyral_e2e_web`, migrates it,
  uses Redis logical DB 15 (flushed before each test so the per-IP limit of 30/15 min does not make later
  tests flaky), and creates users with the master's own `createUser` (the function behind
  `admin:create`). TOTP codes are computed in the test with RFC 6238 on `node:crypto`. Covered: first
  login → enrollment (wrong code, then right) → recovery codes (download, confirmation gate) → shell →
  all nav placeholders → logout → protected page bounces to login; returning user TOTP login, step-up
  dialog (wrong then right code), logout everywhere; wrong password and unknown user (same message);
  wrong TOTP then right; recovery-code login (wrong then right, 9 left); screenshots; CSP.
- **Why e2e is not in `pnpm verify`:** it needs the Docker dev stack, a downloaded browser, a master build
  and about a minute. It was run green twice in a row for this change; CI wiring belongs to p1-cicd.

## 6. Proposed master changes (not made here)

1. Optional `/api` route prefix (or serving `apps/web/dist` from the master with `@fastify/static` and an
   SPA fallback) so a single process can serve the console without ingress path rewriting.
2. A way to learn the current **pending** stage (e.g. `GET /auth/session` returning
   `{ stage: 'mfa_pending' | 'enrollment' }` for pending sessions, or a dedicated `GET /auth/stage`) so a
   reload during the second factor/enrollment resumes instead of restarting the login.
3. A package export (or a small test helper module) for `createUser` / `createPool` / `migrate`, so the
   web e2e does not import `apps/master/dist/*` internals by path.
4. Optional env overrides for the auth rate limits in `NODE_ENV=test` (the e2e currently flushes its
   dedicated Redis DB instead).

## 7. Rollback and operations

The console is static files with no server state: rollback = deploy the previous `dist/`. It changes no
master behaviour and no database schema. Operational signals remain the master's (`auth.*` audit events,
`/readyz`). Browser support: evergreen Chromium/Firefox/Safari (ES2023, native `<dialog>`); Safari on
plain-HTTP localhost is unverified (see admin-bootstrap §6).
