# Design note: `p2-service-linux`, `p2-service-macos`, `p2-service-windows`

- **Tasks:** OS-native worker installers and service-manager integration for Linux (x64/arm64 incl. Raspberry Pi OS 64-bit), macOS and Windows. Acceptance **A-FLEET-4**: the worker daemon survives a process crash and a reboot and restores its correct status.
- **Date:** 2026-10-13
- **Binding inputs:** ADR-0002 (Node 24; packaging left open → decided here), ADR-0005 (device key in the OS keystore or a 0600 file owned by the service user), **ADR-0007** (a dedicated low-privilege OS user is mandatory on macOS, Windows and the Pi; the workspace lives under a worker-owned root), threat model T-SBX-1, T-SBX-5, T-SUP-2, T-WRK-1, `p2-worker-core` (config locations, exit 78, permission checks, durable store).
- **Out of scope:** auto-update and signature verification (`p2-signed-updates`), OS keystores (Keychain/DPAPI backends are still fail-closed stubs), per-job sandboxing (`p3-sandbox`), the container profile's rootless engine setup (documented as an optional owner step), pairing UX (`p2-pairing`, `docs/ops/worker-pairing.md`).

## Problem

`remyral-worker run` exists, but nothing starts it at boot, restarts it after a crash, runs it as a dedicated low-privilege account, or tells the owner what state it is in. Each OS has its own service manager with different stop semantics, restart policies and log sinks; the daemon's contract with all of them has to be the same: *crash → restart; clean stop → exit 0 after cancelling jobs; configuration error (exit 78) → no restart loop; restart → status restored from the durable store*.

## Shape

```
infra/worker/
  linux/   install.sh · uninstall.sh · remyral-worker.service · restart-backoff.conf
           test/ Dockerfile · systemd-e2e.sh (host driver) · in-container.sh · wait-active.sh
  macos/   install.sh · uninstall.sh · com.remyral.worker.plist
  windows/ install.ps1 · uninstall.ps1 · test/ (plan tests with fakes)

apps/worker/src/service/
  definitions.ts   per-OS names, accounts, paths, no-restart exit codes, stop timeout
  manager.ts       read-only queries + parsers: systemctl show / launchctl print / sc.exe queryex+qc
  status-file.ts   <dataDir>/status.json writer (daemon side) + runWorkerWithStatusFile
  early-signals.ts latch for stop requests that arrive during startup
  status.ts        `service status`: manager state + status.json + read-only store summary
  command.ts       CLI handler (registered in cli.ts with two clearly marked lines)
```

## Decisions

### Packaging (ADR-0002 left this open) — ship the single-file bundle, require Node 24

| | Bundle (`remyral-worker.mjs`) + system Node 24 | Node SEA (single executable) |
|---|---|---|
| Node 24 support | Plain ESM bundle, already built and smoke-tested (`p0-worker-probe`, `p2-worker-core`) | SEA in Node 24 runs **only a CommonJS** main script, needs `--experimental-sea-config` + `postject`, signature removal/re-signing on macOS and Windows (nodejs.org v24 docs) |
| Artifacts | 1 file (~0.9 MiB) for every OS/arch | 6 binaries (3 OS × 2 arch), ~100 MiB each |
| Updates / signing (`p2-signed-updates`, T-SUP-2) | Sign and verify one small file with a pinned key; atomic swap of one file | Re-sign whole binaries per platform (Apple notarization, Authenticode), large downloads on residential links |
| Node security fixes | From the OS/vendor channel (NodeSource apt, nodejs.org pkg/msi), independent of our release | Only when we rebuild and ship every binary |
| Risk | Owner must install Node 24; a later major upgrade could break the worker | No external dependency |

**Decision:** ship the bundle and require a **system-wide, root/admin-owned Node 24** (installers refuse anything else, see T-SUP-2 below). The installers check `node --version` = v24.x. Revisit SEA when it supports ESM and once the signed-update channel exists (record it in the `p2-signed-updates` ADR). Installers accept `--bundle-sha256`/`-BundleSha256` and refuse a mismatching bundle; real signature verification is `p2-signed-updates`.

### Common contract between daemon and service managers

1. **Exit codes:** 0 = graceful stop (no restart). 78 (`EX_CONFIG`, from `p2-worker-core`) = bad config/permissions/keystore → **not restarted** where the manager can express it (systemd `RestartPreventExitStatus=78`, shawl `--restart-if-not 0,78`); launchd cannot exclude exit codes, so it retries every `ThrottleInterval` (documented). Anything else (2 = crash, 1 = unhandled rejection, signals) → restart.
2. **Stop:** the manager sends SIGTERM (systemd, launchd) or Ctrl-C (shawl on Windows → Node `SIGINT`) to the **daemon only**; the daemon terminates its job process trees (10 s grace each, in parallel), flushes the store and exits 0. Managers wait **60 s** before killing what is left (`TimeoutStopSec`, `ExitTimeOut`, `--stop-timeout`), well above the 10 s child grace.
3. **Stop during startup (bug found by the systemd e2e test):** `bin.ts` swallows the first SIGTERM (it implements "second signal forces exit") and the daemon subscribed to signals only inside `WorkerDaemon.start()`, after config/store/key loading. A stop in that window was lost and systemd SIGKILLed the daemon after 60 s. `latchShutdownSignals` subscribes before the first `await` and replays the request to the daemon. Regression test: real process, SIGTERM right after the first log line → exit 0 within 10 s (fails without the latch).
4. **Status across restarts (A-FLEET-4):** the daemon's lifecycle state is *derived from the durable store* on start (`p2-worker-core` decision 15: enrollment, leases, cursors survive; restored leases are not running jobs; an enrolled worker reconnects to `online`, not `pending`, and does not show a pairing code). For the owner, `runWorkerWithStatusFile` mirrors the state machine into `<dataDir>/status.json` (0600, atomic) on start, on every transition and on graceful stop (`stopped` + reason). It is a report, never an input. A crash leaves the last live record; `service status` marks it **stale** when the recorded pid is not the manager's main pid (systemd/launchd start node directly; under the Windows SCM the service pid is shawl's, so there only `running`/`stopped` is compared).
5. **`remyral-worker service status [--config] [--json]`** is read-only: it asks the manager (`systemctl show -p …`, `launchctl print system/<label>`, `sc.exe queryex` + `qc`), reads the config without creating `dataDir`, reads `status.json` and summarizes `state.json`/`outbox.jsonl` without repairing or quarantining them. Exit codes follow LSB `status`: 0 running, 3 installed but not running, 4 not installed/unknown. `sc.exe` values are parsed by number (state names are localized). Permission errors say "run as root/Administrator, or as the service user".
6. **Workspace and data live under one worker-owned root** (ADR-0007): Linux `/var/lib/remyral-worker/{workspaces,home}`, macOS `/Library/Application Support/RemyralWorker/data/{workspaces,home}`, Windows `%ProgramData%\RemyralWorker\{data,workspaces}`. Config is root/admin-owned and only readable by the service account; the account cannot rewrite it (T-WRK-1: no redirect to a rogue master).
7. **Idempotent installers with `--dry-run`:** every state-changing command goes through one `run` function that prints it (`+ cmd`, or `[dry-run] cmd` without executing). Files are compared (content + owner + mode) and only rewritten when different; the service is restarted only if the bundle, config or unit changed. An existing config is never overwritten without `--replace-config`. Uninstall keeps config, key, state and workspaces unless `--purge` (purge = re-pairing).

### Linux (systemd) — `p2-service-linux`

8. **Account:** `useradd --system --user-group --home-dir /var/lib/remyral-worker/home --no-create-home --shell $(command -v nologin)`; password locked; an existing account with a login shell is refused. Layout: `/opt/remyral-worker` (root 0755, bundle 0644 — read-only for the worker), `/etc/remyral-worker` (root:remyral-worker 0750, `config.json` 0640), `/var/lib/remyral-worker` (remyral-worker 0700; `dataDir`, home and workspaces), `/usr/local/bin/remyral-worker` CLI wrapper.
9. **Unit** (`Type=exec`, `User=remyral-worker`): `Restart=on-failure`, `RestartSec=5s`, `RestartPreventExitStatus=78`, `StartLimitIntervalSec=0` (never give up on an unattended machine); exponential backoff via a drop-in (`RestartSteps=8`, `RestartMaxDelaySec=5min`) installed **only on systemd ≥ 254** (Debian 12 / Raspberry Pi OS bookworm ship 252 and would warn about unknown keys). `KillMode=mixed` (SIGTERM to the daemon only, SIGKILL to the whole cgroup after `TimeoutStopSec=60s`), `OOMPolicy=continue` (an OOM-killed agent must not stop the service — the default `stop` would). Logs: stdout/stderr → journald, `SyslogIdentifier=remyral-worker`.
10. **Hardening:** `NoNewPrivileges`, `CapabilityBoundingSet=` (empty), `AmbientCapabilities=`, `RestrictSUIDSGID`, `LockPersonality`, `ProtectSystem=strict` + `ReadWritePaths=/var/lib/remyral-worker` (+ a custom workspace root), `ProtectHome=true` (the interactive user's `~/.ssh`, browser profiles, keyrings are invisible — T-SBX-1), `PrivateTmp`, `PrivateDevices`, `ProtectKernel{Tunables,Modules,Logs}`, `ProtectControlGroups`, `ProtectClock`, `ProtectHostname`, `ProtectProc=invisible`, `RestrictRealtime`, `RemoveIPC`, `SystemCallArchitectures=native`, `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK`, `UMask=0077`, `TasksMax=4096`. `systemd-analyze security`: **3.6 OK**. Deliberately **not** set: `MemoryDenyWriteExecute` (breaks V8's JIT), `RestrictNamespaces`/`SystemCallFilter` (break bubblewrap-based runtime sandboxes, e.g. Claude Code on Linux), `ProcSubset=pid` (hides `/proc/cpuinfo`/`meminfo` used by facts/probe). Tightening per profile is `p3-sandbox`.
11. **Node** must be v24, root-owned and not group/world-writable (file and directory), and not under `/home`, `/root`, `/run/user` (nvm installs are invisible under `ProtectHome` and user-writable). `--allow-unsafe-node` exists, warns loudly.
12. **Container profile is a separate, optional owner step** (not forced): rootless Docker/Podman needs `newuidmap`/`newgidmap` (setuid/file caps), which `NoNewPrivileges`/`RestrictSUIDSGID` deliberately break inside this unit. The engine must therefore run in its own user service for `remyral-worker` (`loginctl enable-linger remyral-worker` + `dockerd-rootless-setuptool.sh install` or `podman.socket`), and the worker only talks to its socket via a drop-in (`Environment=DOCKER_HOST=unix:///run/user/<uid>/docker.sock`, `ReadWritePaths=/run/user/<uid>`). Never the root Docker socket (T-SBX-3). Documented in `docs/ops/worker-install.md`; wiring is `p3-sandbox`.

### macOS (launchd) — `p2-service-macos`

13. **Account:** hidden role account `_remyralworker` created with `dscl` (UID/GID = first free id in 400–499, `IsHidden 1`, `UserShell /usr/bin/false`, `Password *`, home under the data dir). `sysadminctl -addUser` is not used: it creates a regular login user (password, secure-token prompts, appears at the login window). Layout: `/Library/Application Support/RemyralWorker` (root:_remyralworker 0750; `config.json` root:_remyralworker 0640, `bin/remyral-worker.mjs` root 0644), `…/data` (_remyralworker 0700 — `dataDir`, home, workspaces), `/Library/Logs/RemyralWorker` (_remyralworker:admin 0750, log file pre-created 0640 so its owner does not depend on launchd). The role account is not in `staff`, so it cannot read users' homes (`/Users/<name>` is 0750 user:staff). Without a config the plist is not installed at all (it would exit 78 every 10 s from boot). Log rotation: macOS `newsyslog` can only rename + signal, and launchd keeps writing to the renamed file, so rotation is left to `p6-observability` (log shipping); the volume is small redacted JSON.
14. **LaunchDaemon** `/Library/LaunchDaemons/com.remyral.worker.plist` (root:wheel 0644): `UserName`/`GroupName`, `RunAtLoad`, `KeepAlive {SuccessfulExit: false}` (restart after a crash, stay down after a clean exit), `ThrottleInterval 10`, `ExitTimeOut 60`, `ProcessType Standard` (`Background` would throttle CPU and I/O of agent jobs), `WorkingDirectory` + `HOME` inside the data dir, `SoftResourceLimits.NumberOfFiles 65536`, no `AbandonProcessGroup` (launchd kills leftover job processes of the group), stdout/stderr → `/Library/Logs/RemyralWorker/remyral-worker.log`, `Umask 63` (077). Loaded with `launchctl bootstrap system` (after `launchctl enable`), restarted with `launchctl kickstart -k` when only bundle/config changed, booted out and bootstrapped again when the plist changed (launchd re-reads it only on bootstrap), removed with `launchctl bootout`. `plutil -lint` validates the shipped and the rendered plist. Node: the nodejs.org `.pkg` (`/usr/local/bin/node`, root:wheel); Homebrew's user-owned Node is refused unless `--allow-unsafe-node`. The installer is bash 3.2-compatible (macOS `/bin/bash`).

### Windows (SCM) — `p2-service-windows`

15. **Account: virtual service account `NT SERVICE\RemyralWorker`** rather than a local user: no password to generate, store or rotate (a local user's password would have to live in the SCM's LSA secret and in our installer's memory); cannot log on interactively or over the network; gets its own SID that ACLs can name; the SCM grants "Log on as a service" itself. Trade-off: no `runas` into it for interactive runtime logins — provider credentials come from the master per job (`p3-secrets-worker`), so none are needed.
16. **Wrapper: shawl v1.9.0** (MIT, Rust, 2026-05-03, actively maintained; pinned with SHA-256 of the release zip `f883c5d0…351c` and of `shawl.exe` `0985555b…7c6d`) instead of WinSW (last stable v2.12.0 from 2023-01, v3 still alpha) or NSSM (unmaintained since 2017). shawl sends **Ctrl-C** on stop (Node sees `SIGINT`, which the daemon handles on Windows), waits `--stop-timeout 60000`, kills the process tree via a Job Object (`--kill-process-tree`), restarts the command with `--restart-if-not 0,78` and `--restart-delay`, and writes rotated log files (`--log-dir`). The service itself is created with the normal Windows APIs (`Win32_Service.Create` with `StartName = NT SERVICE\RemyralWorker`, then `sc.exe config start= delayed-auto`, `sidtype unrestricted`, `failure … restart/10000/restart/30000/restart/60000`, `failureflag 0`) — shawl needs no installer of its own. Logs: shawl writes rotated files (`remyral-worker_rCURRENT.log` for the daemon's JSON lines, `shawl_rCURRENT.log` for the wrapper, 10 MiB × 5) to `%ProgramData%\RemyralWorker\logs`; start/stop/crash events go to the System event log via the Service Control Manager. A custom event source was not added: `New-EventLog` does not exist in PowerShell 7 and the daemon's logs are already in files. SCM recovery actions restart shawl if *it* dies; `failureflag 0` keeps the SCM from restarting on the exit-78 service-specific error.
17. **ACLs:** `%ProgramData%\RemyralWorker` with inheritance removed: SYSTEM + Administrators full control, `NT SERVICE\RemyralWorker` read on the root/config, modify on `data`, `workspaces`, `logs`. Program files under `%ProgramFiles%\RemyralWorker` (inherited: Administrators/SYSTEM full, Users read/execute). ACEs are granted by SID (`*S-1-5-18`, `*S-1-5-32-544` and the service SID `S-1-5-80-3774447913-1121012858-1807591220-3532974647-2057738445`, computed like `sc.exe showsid`: SHA-1 of the upper-cased UTF-16LE service name — verified against the well-known TrustedInstaller SID), so ACLs work on localized Windows and before the service exists. ACLs and the recovery settings are re-applied on every run (idempotent); everything else only when it differs. The service is created and re-pointed through `Win32_Service.Create`/`Change` (CIM) rather than `sc.exe create binPath= …`, which avoids PowerShell 5.1's native-argument quoting problems with the quoted ImagePath; the ImagePath itself is built with `CommandLineToArgvW` quoting rules (tested). The config is written as UTF-8 without BOM (the loader also strips a BOM).
18. **Testability:** `install.ps1` builds a *plan* (list of actions) from injectable probes (a hashtable of scriptblocks); `-DryRun` prints the plan and executes nothing. Plan tests (`test/Install.Tests.ps1`, plain assertions, no Pester) run with fakes in PowerShell 7.6.6 in Docker (`test/run-tests.sh`; pinned tarball, SHA-256 checked — the mcr image has no arm64 variant): parse check incl. a scan for PowerShell 7-only operators, service SID vector, quoting, fresh install, idempotent re-run, update+restart, LocalSystem → virtual account, validation, no-config, custom workspace ACL, dry-run printing, uninstall/purge plans. The daemon needs no SCM-specific stop hook: shawl's Ctrl-C arrives as `SIGINT`, which `nodeShutdownSignals` already handles on Windows (the `requestStop` placeholder in `daemon/signals.ts` stays unused).

## Security review

| Threat | Mitigation | Residual / follow-up |
|---|---|---|
| T-SBX-1 agent reads/writes outside the workspace | Dedicated no-login system account per OS; Linux: `ProtectHome`, `ProtectSystem=strict`, only the worker root writable (verified from inside the unit's mount namespace: `~node/.ssh` unreadable, `/usr` and `/opt` read-only even for root, config not writable); macOS/Windows: data root owned by the role account, other users' homes not readable by it by default | macOS has no namespace isolation; the role account can still read world-readable files. Per-job sandboxes: `p3-sandbox`, escape suite `p7-sandbox-escape` |
| T-SUP-2 malicious daemon update / binary swap | Bundle and program dirs root/admin-owned and read-only to the service account; installers refuse a user-writable Node (an attacker who can replace `node` runs as the worker); `--bundle-sha256` | Signature verification and the privileged updater: see [p2-signed-updates](p2-signed-updates.md) (installers accept `--manifest/--signature`) |
| T-WRK-1 key theft / config tampering | `dataDir` 0700 / ACL'd to the account; config root-owned 0640 (account can read, not write); `identity show` must run as the service user (as root it would create a root-owned key the daemon refuses) | File keystore readable by root/Administrators; OS keystores not implemented |
| T-SUP-3 compromised third-party wrapper (Windows) | shawl pinned to v1.9.0; release zip and `shawl.exe` SHA-256 verified before use (download over TLS from GitHub, or offline `-ShawlZip`); installed under `%ProgramFiles%` (admin-writable only) | Trust in the upstream maintainer and GitHub release integrity; no Authenticode signature on shawl. Updating the pin is a reviewed change |
| Windows service account | Virtual account `NT SERVICE\RemyralWorker`: no password, no interactive/network logon, own SID; data root ACL'd to SYSTEM, Administrators and that SID only (by SID, localization-proof) | Not a member of `Users`-only resources by design; other world-readable files remain readable. Host-restricted profile on Windows stays weaker than Linux (ADR-0007 consequence) |
| T-SBX-5 resource exhaustion | `TasksMax=4096`, `LimitNOFILE`; `OOMPolicy=continue` keeps the daemon alive | Memory/CPU quotas per job: `p3-sandbox`, `p4-quotas` |
| Privilege escalation via the unit | No capabilities, `NoNewPrivileges`, `RestrictSUIDSGID`, `LockPersonality`; exposure 3.6 | — |
| Restart loops / silent failure | Exit 78 not restarted (systemd, shawl); `StartLimitIntervalSec=0` + backoff; `service status` shows last exit/signal and stale state | launchd retries exit 78 every 10 s (logged) |
| Lost stop → SIGKILL of running jobs | Latched shutdown signal (regression-tested); `KillMode=mixed`; 60 s stop timeout | Windows pre-shutdown: the SCM gives services only a few seconds at OS shutdown (shawl does not register for pre-shutdown) — **UNVERIFIED** |
| Logs leak secrets | Daemon logs are already redacted JSON (`p2-worker-core`); log dirs readable only by the account and admins | journald is readable by `adm`/`systemd-journal` members |

## Platform verification status

- **Linux arm64:** verified against real systemd in Docker on Debian 13 and 12 (aarch64). **UNVERIFIED on x64** (qemu-user emulation cannot run systemd's sandboxing — run `systemd-e2e.sh` on an x64 CI runner) and **on Raspberry Pi hardware** (`p2-arm64`).
- **macOS:** shipped plist and the rendered plist pass `plutil -lint` (macOS 26, arm64); `install.sh --dry-run` and `uninstall.sh --dry-run --purge` run on this Mac and in tests with read-only `dscl`/`launchctl` fakes that fail on any write (first free id, existing/refused accounts, no-config, reload paths, input validation). **UNVERIFIED: a real install** (account creation, launchd crash restart, reboot) — by instruction no account was created and no daemon loaded on the development Mac; run it on the fleet Mac (blocking integration ticket for the P2 gate).
- **Windows:** plan logic verified with fakes under PowerShell 7.6.6 (56 assertions), shipped constants checked against the daemon by vitest; shawl v1.9.0 release zip SHA-256 matches GitHub's published digest. **UNVERIFIED on real Windows**: Windows PowerShell 5.1 parsing/execution, the real probes (`Get-Acl`, CIM), service creation with the virtual account, ACL effect, shawl Ctrl-C → graceful stop, SCM recovery and reboot. The Windows PC (`desktop-pc`) was unreachable over SSH during this task (port 22 timed out), so not even the read-only `-DryRun` could run there — blocking integration ticket for the P2 gate: run `install.ps1 -DryRun`, then a real install on a test machine, kill `node.exe` (restart), `Stop-Service` (exit 0), reboot.## Rollback

`uninstall.sh` removes service, unit and program files and keeps config/key/state (re-install resumes with the same identity); `--purge` removes everything incl. the account (the worker must then be revoked in the dashboard and re-paired). Worker code changes are additive (`src/service/`, two marked lines in `cli.ts`); reverting the commit restores `run` without the status file.

## Operational metrics

`service status` exposes restarts (`NRestarts`/launchd runs), last exit code/signal, and stale status — inputs for `p2-heartbeat-caps`/`p6-alerts` (alert on restarts > N/hour, exit 78, stale). Log events: `worker daemon starting` (with `leasesAwaitingReconciliation`), `could not write the status file`.
