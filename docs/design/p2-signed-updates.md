# Design note: `p2-signed-updates` — signed, separately authenticated worker auto-update with rollback

- **Task:** `p2-signed-updates` (ROADMAP P2). ARCHITECTURE "Deployment": *deploy worker as OS-native service with separately authenticated updates*. Threat model **T-SUP-2** (malicious worker daemon update pushed through our updater).
- **Date:** 2026-10-13
- **Binding inputs:** ADR-0011 (protocol versioning: additive minor changes, unknown types ignored), ADR-0005 (device identity, outbound-only TLS 1.3 WebSocket), ADR-0004 (leases: a restart cancels jobs, the master reconciles), ADR-0009 (admin + step-up for privileged actions), `p2-service-install` (single-file bundle `remyral-worker.mjs` + root/admin-owned Node 24; install dir root-owned and read-only for the service account; hardened units), `p5-rbac` (every route declares `config.authz`, deny by default).
- **Out of scope:** updating the privileged updater itself or Node (both only through the installers / the OS vendor), OS keystores, Node SEA packaging (still not revisited: SEA in Node 24 is CommonJS-only, see `p2-service-install`; the signed-bundle channel built here works unchanged for SEA binaries later), multi-replica fan-out of offers (single master replica, like the rest of `src/workers/`).

## Problem

Workers sit on residential machines the owner rarely touches. Updating them by hand does not scale, but an updater is the most attractive target in the system: whoever controls it runs code as the worker on every machine (T-SUP-2). The master is on a public cloud VM and must be assumed compromisable; the worker service account must be assumed compromisable too (it runs agents on untrusted repositories). Neither may be able to make a machine run code the release owner did not sign — and a bad but genuine release must not brick the fleet.

## Decisions

### 1. Release signing: one offline Ed25519 key, signatures over exact manifest bytes

- A release is `remyral-worker.mjs` + `manifest.json` `{schema, name, version, channel, protocolVersions, minNode, sha256, size, createdAt}` + `manifest.sig.json` `{keyId, signature}`. The signature covers `remana-worker-release/v1\n` ‖ *the manifest file's bytes* — no canonical JSON, nothing to normalise; the verifier checks the signature **before** parsing. The domain prefix makes a release signature unusable as an AUTH or rotation signature and vice versa.
- The **release key is separate** from the master's lease-signing key (ADR-0004) and from device keys (ADR-0005). It is generated by `sign.mjs keygen` into a 0600 PKCS#8 file that stays **off the control plane** (owner's machine / hardware token / offline backup; `sign.mjs` refuses a key file readable by group/others). The master gets only the public key(s) (`RELEASE_PUBLIC_KEYS`) and **cannot sign**.
- `keyId` = first 16 hex chars of SHA-256(raw public key); verification selects the key by id and still verifies (a forged id fails `bad_signature`).
- **Pinning:** `sign.mjs build` compiles the public key (and, during a rotation, the next one: `--also-trust`) into both bundles via esbuild `define` (`__REMYRAL_RELEASE_KEYS__`), together with the version (`__REMYRAL_WORKER_VERSION__`). The root-owned worker config may **replace** the compiled-in keys with `updates.releaseKeys` (1–2 keys) — this is how a key is rotated or retired without trusting the master. A source/dev build has no compiled key and accepts no update unless the config names one.
- Rotation overlap: release N pins `{K, K′}` and is signed with K; release N+1 is signed with K′ and may pin only K′. The privileged updater is not auto-updated, so its trust follows the config (`updates.releaseKeys: [K, K′]`) or a re-run of the installer.

### 2. Master: registry and intent only — it stores and serves, never signs

- `POST /releases` (admin, `releases.publish`, step-up, CSRF; 48 MiB route body limit for the base64 artifact) accepts the `release.json` document `sign.mjs` writes. It is accepted only if the signature verifies against `RELEASE_PUBLIC_KEYS`, the artifact matches size + SHA-256, and the build speaks a protocol version this master supports (`protocol_incompatible` otherwise). Refusals are audited (`release.upload` denied). Re-uploading identical bytes is idempotent (200); the same version with other bytes is 409. The same bytes re-signed for `stable` upgrade a canary release in place.
- `PUT /releases/channels/:channel` (admin, `releases.publish`, step-up) sets `{version, rolloutPercent}`; `stable` only accepts a release *signed* for stable (`channel_mismatch`). `GET /releases` (`releases.read`, viewer) lists releases, channels and the last 100 attempts (`?workerId=`).
- `POST /workers/:id/update` (admin, `workers.update`, step-up) sets the worker's channel and/or an explicit **target** (`version`, `rollback`, `force`). A target pins the worker (channel promotions stop applying) until a request with only `channel` clears it. A lower version without `rollback: true` is 409 `downgrade_requires_rollback`.
- Storage (migration **0013**): `worker_releases` (exact manifest bytes, signature, artifact `bytea` ≤ 32 MiB — the bundle is ~1.1 MiB and Postgres is the source of truth, ADR-0003), `worker_release_channels`, `worker_update_targets`, `worker_update_attempts` (status, reason, hashed download token, at most one open attempt per worker — partial unique index).
- **Rollout determinism:** bucket = first 4 bytes of SHA-256(`remyral-rollout/v1\n<version>\n<workerId>`) mod 100; a worker is in the rollout iff bucket < percent. Raising the percentage only adds workers; different releases pick different first workers. A channel never offers a version ≤ the worker's own (no downgrades through channels).
- **Offers:** computed on every session start and after every intent change for connected workers (`offerToConnected`). A version that failed / rolled back / was refused on a worker is not re-offered automatically (an admin re-targets to retry). An attempt in `activating` is never re-offered (the worker is restarting into it). Open attempts without a final report time out after 1 h (`timed_out`).

### 3. Protocol: two additive 1.0 messages (ADR-0011)

No existing message fits: `UPDATE_POLICY` is the job-policy message and is sequenced; `ROTATE_CREDENTIAL` is identity. Added as **control messages (seq 0)** because the durable intent lives in Postgres and is re-evaluated per session (like DRAIN):
- `UPDATE_AVAILABLE {attemptId, version, channel, sha256, size, manifestUrl, artifactUrl, downloadToken, tokenExpiresAt, rollback, force}` — URLs are schema-restricted to `/v1/worker/releases/<version>/{manifest,artifact}` on the master origin.
- `UPDATE_STATUS {attemptId, version, phase, reason?, detail?, currentVersion}` with phases `downloading | deferred | activating | succeeded | rolled_back | failed | refused`. The master accepts a report only for the reporting worker's own attempt; terminal outcomes are final and audited (`worker.update.<phase>`).
- Pre-updater workers drop `UPDATE_AVAILABLE` as an unknown type (ADR-0011 §4; one invalid-frame warning per offer, far below the disconnect threshold) — they need one manual reinstall with the updater. Previous-release contract tests (ADR-0011 Verification) are not automated yet: **follow-up** (needs two published releases).

### 4. Download: HTTPS on the master origin, authenticated by a worker-scoped token

`GET /v1/worker/releases/:version/{manifest,artifact}` (route auth level `device`, no human session). The bearer token comes only over the worker's authenticated WebSocket, is 32 random bytes (stored as SHA-256), bound to one worker, one release and an open attempt, valid 15 min, dead once the attempt ends, rejected for quarantined/pending workers, rate-limited per IP. The worker derives the origin from its `masterUrl` (`wss→https`, TLS 1.3, certificate verification on, no redirects, no compression, streaming size cap = the signed size). The WebSocket was not used for the artifact: frames are capped at 512 KiB and the bundle is >1 MiB. **Integrity never depends on this channel** — the token only keeps the artifact from being an anonymous download.

### 5. Worker side: verify, stage in the data dir, ask — never activate

The daemon's `UpdateAgent` (`apps/worker/src/update/agent.ts`; the daemon only got four hook calls) checks, in order: updates enabled, a trusted key exists, channel (a `stable` machine refuses canary offers *and* canary-signed manifests), **downgrade** (lower than the running version only with `rollback`; never below the owner floor `updates.minVersion`), the updater not mid health-check; then downloads and verifies the manifest signature with its pinned keys, that the manifest matches the offer, that the build speaks the **negotiated protocol version** of the current session, `minNode` ≤ running Node, and the artifact size/SHA-256. Only then it stages manifest, signature and artifact under `<dataDir>/updates/staged/<version>/` (0600).

**Jobs:** if jobs run and the offer is not `force`, it reports `deferred`, **drains itself** (no new jobs; the master sees `draining`) and waits; a master-requested DRAIN is never undone by it. Then it writes `<dataDir>/updates/request.json` atomically, moves the state machine to `updating`, reports `activating` and waits. If no updater acts within 5 min it reports `failed: updater_unavailable`, removes the request and reconnects. A forced update restarts with jobs running: they are cancelled by the graceful stop and reconciled by the master (ADR-0004).

### 6. Privileged updater: a separate root/SYSTEM process started by the service manager

The install dir is root-owned and read-only for the worker (hardened unit: `ProtectSystem=strict`). Options were (a) give the worker write access — rejected: an agent escape could then replace the code that runs at every restart; (b) let the worker run a setuid/sudo helper — rejected: `NoNewPrivileges`/`RestrictSUIDSGID` forbid it by design and it would be a privilege-escalation surface; (c) **a separate privileged helper started by the service manager**, which treats everything in the data dir as hostile input. Chosen: (c).

- **Trigger:** Linux `remyral-worker-update.path` (`PathChanged=` on the request file) starts the oneshot `remyral-worker-update.service` as root; macOS LaunchDaemon `com.remyral.worker.updater` with `WatchPaths`; Windows scheduled task `RemyralWorkerUpdater` as SYSTEM every minute (Windows has no path-triggered start). All also run at boot to resume an interrupted health check. The worker can only *write a hint*; it cannot start, stop or parameterise the updater (arguments are fixed in root-owned unit files).
- **Re-verification:** request and staged files are read with `O_NOFOLLOW | O_NONBLOCK`, must be regular files, size-capped, and parsed with strict schemas; the signature is verified again with the **updater's own** pinned keys (compiled in / root-owned config), plus artifact hash, channel, Node, downgrade rule (`rollback` flag) and owner floor. The bytes that were verified are the bytes written — never re-read from the staging path (no TOCTOU). The updater never deletes or writes anything in the worker's data dir (no root writes through worker-controlled paths); attempts are de-duplicated by id in its own state.
- **Activation:** the verified copy goes to `<install>/versions/<version>/` (root, 0644), the currently active bytes are retained (also an unsigned dev install, addressed as `unversioned-<sha12>`), then the **active bundle is replaced by one atomic rename** of the verified bytes onto `<install>/remyral-worker.mjs` — the path every service definition, the CLI wrapper and Windows' shawl command line already execute, so no unit changes were needed and the switch is atomic on all three OSes (`rename(2)`, `MoveFileExW(REPLACE_EXISTING)`). `state/active.json` records which version that is; the version is always recomputed from the bundle's SHA-256, never trusted from a name. State (`phase: health_check`, target, previous) is persisted **before** the switch, so a crash or reboot resumes the check (and rolls back if needed). Three versions are retained.
- **Restart + health check:** `systemctl restart` / `launchctl kickstart -k` / `net stop && net start`. Healthy = the new daemon wrote `<dataDir>/update-health.json` with the **new version**, a heartbeat time after the restart, and (systemd/launchd) the service manager's **main PID** — i.e. it connected, received SESSION_ESTABLISHED and sent its first HEARTBEAT within `updates.healthTimeoutSec` (default 90 s). Otherwise the previous bytes (hash-checked) are switched back, the service restarted and the outcome `rolled_back: health_check_failed` recorded. The outcome goes to `<install>/state/last-result.json` (root-owned, world-readable); the running daemon reports it with UPDATE_STATUS (and remembers what it reported).
- **Hardening of the Linux unit:** `PrivateNetwork=yes` (it downloads nothing), `ProtectSystem=strict` with only `/opt/remyral-worker` writable, the data dir read-only, `ProtectHome`, `NoNewPrivileges`, `CapabilityBoundingSet=CAP_DAC_READ_SEARCH CAP_DAC_OVERRIDE` (read the 0700 data dir), `RestrictAddressFamilies=AF_UNIX` (systemd's socket), `UMask=0022`.
- **The updater itself and Node are not auto-updated.** They change only through the installers (which verify signed bundles through the same updater: `adopt`), keeping root-level code changes a deliberate owner action.

### 7. Installers (additive)

New flags: `--manifest/--signature` (`-Manifest/-Signature`): the bundle is verified and activated through `remyral-worker-updater.mjs adopt` (versions layout, downgrade refused, `--allow-downgrade` only by hand); `--updater` (default: next to the bundle); `--release-public-key` (written to a *new* config as `updates.releaseKeys`). Without a manifest the old unsigned path is unchanged (with a warning) and `--bundle-sha256` still works. `--dry-run`/`-DryRun` print every new step. Uninstallers remove the updater units/task; versions and state live in the program dir and go with it.

## Security review

| Threat | Mitigation | Residual / follow-up |
|---|---|---|
| T-SUP-2: compromised master pushes its own code | The master holds only public keys; workers verify with keys pinned in their build or root-owned config; the privileged updater verifies again with its own keys | A stolen **release key** defeats this: keep it offline (doc); rotation via `updates.releaseKeys` on each machine; no transparency log / threshold signatures yet |
| Compromised master pushes an **old, vulnerable but signed** release (downgrade / rollback attack) | Lower versions only with an explicit `rollback` flag (admin + step-up + audited); worker *and* updater refuse otherwise; owner floor `updates.minVersion` (root config) is absolute | A compromised master can still set `rollback: true` down to the floor; set the floor after security releases. No signed revocation list yet |
| Compromised master serves a different artifact for a signed manifest / tampers manifest bytes | Signature over exact bytes + SHA-256 + size; size cap while streaming | — |
| Canary build reaching production machines | Channel is part of the signed manifest; `stable` machines refuse canary-signed builds (worker and updater); `stable` channel refuses canary-signed releases on the master | Opting a machine into canary is a root config change by design |
| Compromised **worker account** (agent escape) plants files / symlinks / FIFOs for the root updater | Updater reads only bounded regular files without following symlinks, verifies signatures on the bytes it read, writes only into the root-owned install dir, never deletes or writes in the data dir; request is a hint with schema-checked fields; attempt ids de-duplicated; e2e: forged request refused | The worker account can trigger re-activation of *signed* versions ≥ floor (same power as the master's rollback) — DoS by restart loops is bounded by the health check and by the service manager |
| Compromised worker account replaces the running code directly | Install dir root-owned, `ProtectSystem=strict`; verified in the systemd e2e | macOS/Windows rely on file ACLs (no namespace) — as before |
| Download endpoint abused (fleet artifact scraping, token replay) | Token from the authenticated WebSocket only, hashed, worker + release + open-attempt bound, 15 min, dies with the attempt; quarantined workers refused; per-IP rate limit | Releases are not secret; confidentiality is not a goal |
| Malicious upload by a non-admin / without second factor | `releases.publish` / `workers.update` admin-only (authz matrix), fresh step-up, CSRF, audited incl. refusals | — |
| Bricked fleet by a genuine bad release | Rollout percentage, canary channel, health check with automatic rollback, failed versions not re-offered, crash-resumable state | Health = "connects and heartbeats"; a release that connects but fails jobs is not rolled back automatically (admin rollback) |
| Update during running jobs (side effects, T-OPS-1) | Never without `force`: the worker drains itself first; forced restarts cancel jobs gracefully and leases are reconciled (ADR-0004) | — |
| Updater compromise = root | Separate small bundle, never auto-updated, no network (`PrivateNetwork`), minimal capabilities, fixed arguments | Windows task runs as SYSTEM without namespace restrictions — **UNVERIFIED on real Windows** |
| Secrets in logs | Updater logs ids, versions and reasons only; tokens never logged; download tokens stored hashed | — |

## Platform verification status

- **Linux arm64:** e2e above on real systemd 257 (Debian 13) and 252 (Debian 12 = Raspberry Pi OS bookworm base): 35 checks each. **UNVERIFIED:** x64 (needs an x64 runner), Raspberry Pi hardware.
- **macOS:** installer dry-run with fakes + `plutil -lint` of the updater plist. **UNVERIFIED:** a real install (WatchPaths trigger, kickstart, health check) — blocking integration ticket for the P2 gate, together with the existing macOS item.
- **Windows:** plan tests only. **UNVERIFIED:** scheduled task as SYSTEM, `net stop/start` restart, rename over the active bundle while shawl is stopped, health check without PID comparison (shawl wraps node) — blocking integration ticket.

## Rollback (of this feature)

Set `updates.enabled: false` in a worker's config (the agent then ignores offers) or stop offering by pointing channels at the running version / 0 %. Removing the updater units disables activation entirely (requests time out as `updater_unavailable`). Reverting the code leaves migration 0013's tables unused (forward-only migrations).

## Operational metrics

`worker_update_attempts` (status counts per release, `rolled_back`/`failed` reasons, time from `offered` to `succeeded`), audit events `release.upload`, `release.promote`, `worker.update.target|offer|succeeded|rolled_back|failed|refused`, updater logs (`journalctl -u remyral-worker-update`, `/Library/Logs/RemyralWorker/remyral-worker-updater.log`), `remyral-worker-updater status`. Alert (p6-alerts) on any `rolled_back` and on attempts stuck in `activating`.
